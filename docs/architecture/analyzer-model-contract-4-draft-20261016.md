# Контракт №4: сообщения модели, выполнение и ошибки — предложение

Статус: требуется отдельное решение владельца. №1, №2 и №3 согласованы;
в №3 учтены profile timezone пользователя и смысловые предложения категорий
без молчаливой подмены. Ниже новый контракт, а не описание работающего API.

## Предлагаемая граница

Модель определяет смысл; программа хранит проверенный контекст, разрешает
инструменты, проверяет доступ и считает. Первый ответ модели — компактный
закрытый структурированный план. Текст сообщения пользователя/истории —
данные, не команды менять правила, полномочия или финансовую БД.

На вход понимания даются очищенная текущая просьба, минимально нужная
история этого чата и server-owned календарный контекст (profile timezone,
дата отсчёта). Подтверждённые задачи и неуспешные просьбы различаются.
История не заменяется одним флагом «прошлые задачи есть/нет». Не передаются
пароли, контакты/идентификаторы аккаунта, банковские реквизиты, полные
выписки, скрытые ключи, SQL, внутренние UUID или устаревшие суммы.

После положительного финансового gate программа может по необходимости
дать ограниченный список разрешённых пользовательских названий для
уточнения категории либо результат разрешённого инструмента для объяснения.
Исходные операции/номера счетов для этого не нужны. Общий финансовый вопрос
не требует чтения личных операций; посторонний не даёт доступа к ним/поиску.

## Предлагаемые поля плана

| Поле | Зачем |
|---|---|
| version | Различать версии и не переигрывать старые квитанции по новым правилам |
| topic | Выбрать разрешённую финансовую часть и маршрут ответа |
| action | Читать, объяснять, предложить изменение, уточнить, сообщить отсутствие функции или перенаправить |
| context | Новая задача, продолжение, явный возврат или продолжение неуспешной просьбы |
| changes | Только явно названные изменения параметров; пропуск означает сохранение по №2 |
| needsFreshSources | Для актуального общего финансового факта запросить проверяемый источник, не выдумывать свежие цифры |

Предлагаемые topic: personal_finance (личные данные), general_finance
(общие знания), financial_guidance (финансовые советы и косвенная тема),
mixed (финансовая и посторонняя части), ambiguous (смысл неясен), unrelated
(полностью постороннее). В mixed исполняется финансовая часть. Метка и
action сами не дают технических прав: каждый инструмент проверяет доступ,
ownership, entitlement, актуальность состояния и свою область применения.

context выбирает смысл связи, а не внутренний идентификатор. Фактический
родитель определяется программой среди разрешённых задач. Явная ссылка
передаёт смысл пользовательской ссылки; неизвестную или неоднозначную
связь нельзя заменять последним результатом молча. Неуспешная просьба
переосмысливается из исходного очищенного текста, не из отвергнутого JSON.
Источник переиспользуемых условий и его календарная дата различаются
с текущим сообщением, чтобы сохранять приоритет ручных UI touches и №2.

changes содержит field, op=set/clear/use_current, а value — только для set.
Необязательный source указывает current либо временную метку сообщения
из переданного очищенного history; без source используется current. Программа
проверяет существование источника и применяет его date/timezone snapshot.
Эти метки не являются UUID, правом доступа или модельным сохранённым scope.
Проверка значений зависит от конкретного поля. Нет любых произвольных
ключей, model-generated SQL, UUID, полномочий или вычисленных totals.
Новая задача получает defaults программы; отсутствие поля не равно clear.
Дата/сумма передаются выражением запроса, а вычисляет их программа.
Дублировать один период в равных value и quote не требуется.

Служебные дословные цитаты не обязательны для каждого параметра; отсутствие
заглавной буквы не повод отклонить правильную команду. При этом программа
проверяет типы, диапазоны, несовместимости, разрешённые имена/инструменты и
безопасность выполнения. Это не формальное доказательство полноты понимания
естественного языка — пропуски/выдуманные условия измеряются независимыми
языковыми тестами, а не объявляются устранёнными одной schema validation.

Пример смысла структуры для «А по категориям?»:

```json
{
  "version": "cashneuro-assistant-plan/1",
  "topic": "personal_finance",
  "action": "read",
  "context": { "mode": "continue" },
  "changes": [{ "field": "grouping", "op": "set", "value": "category" }]
}
```

Старые даты и пороги не копируются моделью: их сохранит программа.
Недопустимый пример — молча добавить clear суммы/категории или отмену
сравнения, которого в новой просьбе не было.

## Число вызовов и сбои

1. Простой запрос обычно требует один вызов понимания. Дополнительный
   нужен только для определённой работы: уточнение по разрешённым названиям,
   объяснение полученного результата или исправление структурного ответа.
   Для первой реализации предлагается максимум три модельных вызова на
   одно сообщение, включая исправление; бесконечного tool/retry loop нет.
2. При неправильном JSON/типах разрешена максимум одна автоматическая
   попытка исправить структуру. Она сохраняется отдельно и учитывается в
   стоимости. Нельзя расширять scope, удаляя неудобные поля ради прохода.
   Смысловая неоднозначность требует вопроса пользователю, а не такого retry.
3. Если после отправки неизвестно, был ли запрос обработан/оплачен
   (timeout/обрыв/нет usage), новый платный POST автоматически не делается.
   Отсутствие usage не считается нулевой стоимостью. Для известного ответа
   повтор того же request ID воспроизводит сохранённый результат бесплатно.
4. Раздельные состояния: непонятная просьба; недоступная функция; invalid
   structured response; transport/delivery failure; access/state changed.
   Они не превращаются в unrelated или шутку. Пользователь видит короткую
   понятную причину; технический отчёт содержит фиксированный код и этап.
5. Подтверждённая задача меняется только после успешного разрешённого
   расчёта и атомарного сохранения. Ошибка не стирает её. Новое сообщение
   может продолжить неподтверждённую просьбу по правилам №2.

Финальный текст использует только факты полученного результата. Если
реальная проверка источника для текущей ставки/иного меняющегося показателя
пока недоступна, помощник честно сообщает об этом. Число вызовов, input/output
tokens, фактическая стоимость и неизвестный usage видны в испытательном отчёте.
Лимиты денежных расходов и политика нагрузки отдельно уточняются в №11.

## Внедрение и проверка

Новая версия изолируется от frozen эксперимента и его старых receipts.
Исторические исходы не пересчитываются как улучшенная точность. Для нового
кандидата — отдельная identity, стоимость и явный бюджет испытания; перед
платными вызовами проверяются актуальные тариф/metadata. Production не включается.

Проверки: отсутствие любого поля не сбрасывает фильтры; типы/лишние поля и
неподдержанные действия; никакого финансового чтения при unrelated/ambiguous;
минимальная история и pending recovery без доверия к failed JSON; replay без
оплаты; один repair максимум; общий предел три; unknown delivery без повторного
POST; сохранение последней задачи; человеческие ошибки; отсутствие секретов.
Software checks отдельно от реальных независимых языковых испытаний.
