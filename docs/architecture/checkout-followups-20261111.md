## Проверки

- PostgreSQL 18 с отдельными finance_api/control_api и FORCE RLS: регистрация/повторный код, первая покупка без выписок и POST Анализатора, выдача/возврат пробы, независимые заказы, отмена и поздняя авторизация/возврат, истечение ссылки, сохранение остатков при блокировке, удаление с одним TOTP и повтор запроса. Существующий набор безопасности дополнительно выявил запрет прямой смены quota_policy: сохранён, активация выполняется узкой функцией только по своему оплаченному заказу.
- Браузер desktop/mobile: регистрация с таймером, восстановление ошибок, выбор тарифа при незавершённой пробе, раздельное окно продолжения, порядок кнопок, смена автопродления через «Применить» и сохранение маски карты.
- Production сборки web/admin, TypeScript трёх приложений, хеши продуктовых источников. Платных вызовов моделей и настоящих списаний в проверках нет.

## Установка на Staging

Применяется миграция 0053_checkout_lifecycle.sql. Обновление через scripts/prepare-staging-release.sh с --full-staging --preserve-active-ai: исходные секреты и активные настройки ИИ сохраняются, перед переключением создаётся штатная резервная копия.

В HTTP-уведомлениях тестового магазина ЮKassa добавить payment.waiting_for_capture к существующим payment.succeeded, payment.canceled, refund.succeeded. URL: https://test.cashneuro.ru/api/payments/yookassa/webhook. Фоновая сверка также завершает авторизацию без возвращения пользователя в браузер.

## Ограничение провайдера

Новые интерактивные платежи: capture=false, серверное подтверждение. Отменённый заказ не подтверждается, поздняя авторизация отменяется. API ЮKassa не закрывает страницу pending немедленно; она может оставаться доступной до истечения со стороны провайдера. У старого одностадийного платежа позднее списание полностью возвращается. Нельзя удалить аккаунт с ещё не завершённой внешней отменой. Реальный магазин и банковский возврат проверяются владельцем после установки; локальная проверка использует синтетический провайдер.
