# Письма и напоминания — Development

Основание: полный PDF 38.3–38.8, 39.1/39.11, 40.2/40.8/40.10/40.12/40.15–40.17, 41.11, 43.6, 45.5/45.7; A-07 и E-02/E-04/E-05. Исходные PDF, Word и baseline не изменены. Этот блок зависит от ручного доступа, отдельная ветка `feature/mail-notifications`.

## Поведение

- Закрытый реестр русских текстовых писем: подтверждение заявки/регистрации, приглашение, reset, смена пароля, admin recovery, новый вход с датой и укрупнённым browser/device, существующий аккаунт/приглашение, активация/изменение доступа, claim/решения оплаты и продления, reminders/expiry. Пароли, внутренние причины решений и финансовые операции не включаются. Секретные ссылки используют URL fragment; независимый registration proof остаётся отдельным кодом.
- First-access claim теперь ставит admin notification в той же транзакции, как и renewal claim. В письмо входят account email/name, sender name/bank, expected integer-minor amount, tariff snapshot и канонические creation/claim timestamps. `adminNotificationSentAt` проецируется сервером только после приёма письма **тестовым** ящиком и не является датой перевода.
- Inline предупреждения в аккаунте и над рабочими экранами: 7/3/1 дней, день окончания, expired. API пересчитывает их из canonical cycle; открытый аккаунт обновляется раз в минуту. Истёкший доступ остаётся restricted с renewal flow, без grace period. Бессрочный срок не создаёт предупреждения.
- Finance mail worker ставит email reminders на 7/1 день и после expiry. Московские календарные даты, ключ `user + end + stage`; повторный tick не создаёт дубль. Перед попыткой отправки сверяются актуальные email/verified status/end/indefinite/stage. Продление отменяет устаревшее событие; suspension не снимается и не создаёт entitlement. Срок, который не наблюдался worker на 7/1 день, не отправляется позже с устаревшим количеством дней.
- «Письма» в серверной админке: queued/sent/failed, cumulative attempts, dates, безопасный код ошибки, история ручных повторов. `sent` в этом Development означает принятие sandbox inbox, не доставку/прочтение настоящим адресатом. Active приглашение показывает фактический metadata status. Resend действующего приглашения отправляет ту же ссылку с прежним сроком, не создаёт дубликат при уже queued письме и сохраняет отдельный audit. Повтор после delivery failure также требует TOTP-сессию, reason и action ID; не изменяет ссылку, деньги или срок. Expired/used/cancelled invitation подавляется; для нового срока ссылки нужен existing reissue flow. Reset/verification пользователь запрашивает своим flow; администратор не получает reset URL/proof/payload.

## Очередь и права

- Migration 0005 добавляет token-free `mail.delivery`, resend audit, encrypted sandbox inbox, attempt/retry/lease timestamps и source scope в прежние encrypted outboxes. Переходы metadata проецирует migration-owned trigger с `pg_catalog` search_path и qualified tables; прямой execute отозван. Старые outboxes получают scope по прежним realm/kind. У старых событий subject metadata может отсутствовать до новой issuance; token validity проверяется по verifier.
- `mail_finance` и `mail_control` — отдельные NOLOGIN/NOSUPERUSER/NOBYPASSRLS роли до выдачи локальных credentials оператором. Разные wrapping keys соответствуют ключам API profiles. Mail workers не читают password hashes, sessions, finance или protected keys. Общий access outbox и sandbox разделены RLS. Control API читает лишь token-free delivery projection, без содержимого identity/access писем. Finance metadata ограничена текущим subject; HTTP endpoint её пока не публикует.
- pg-boss **12.37.0** и schemas `jobs_mail_finance/control` установлены оператором в той же migration transaction. Runtime не владеет schema/tables, не создаёт их и стартует с `migrate:false`. Durable `mail-tick` содержит только пустой сигнал, без email/токенов; обработчик дренирует encrypted outbox. Период wake-up 15 секунд. Сбой очереди не откатывает уже завершённую бизнес-транзакцию: outbox остаётся источником работы после рестарта.
- Claim фиксируется до dispatch, lease 30 секунд, до 5 попыток за цикл; временные подтверждённые failures повторяются через 15/30/60/120 секунд. Total attempts сохраняется при admin retry. Произвольные provider exceptions не записываются в DB/logs/API. Неизвестный внешний результат прекращает auto retries. Crash recovery разрешено автоматически лишь для явно idempotent transport; durable sandbox дедуплицирует по delivery ID. Двухфазной транзакции с внешним email provider и гарантии exactly-once внешней отправки нет.
- В поставляемом runtime доступен **только sandbox**: recipient строго `@example.test`, encrypted local inbox, сетевых email calls нет. Запуск Production/Staging и реального SMTP/API transport закрыт. `mail-main.ts` дополнительно требует Development и loopback DB. Postbox выбран последующим реальным провайдером по E-05, но его аккаунт/домен/ключи/доставка не подключены.

## Запуск и проверка

После 0001–0004 локальный Development operator запускает `migrate-mail`. Он устанавливает queue schemas из construction plans и createQueue SQL pinned pg-boss, предварительно снимая их внешние BEGIN/COMMIT, чтобы весь этап был атомарным. Runtime login credentials выдаются отдельно; migration-owner не используется процессом.

`pnpm --filter @finance/api dev:mail` требует APP_ENV=development, MAIL_TRANSPORT=sandbox, MAIL_PROFILE=finance|control, MAIL_DATABASE_URL (loopback и соответствующая mail role), MAIL_WRAPPING_KEY (ключ данного API profile), FINANCE_ORIGIN, CONTROL_ORIGIN, MAIL_ADMIN_RECIPIENT (synthetic owner@example.test). Настоящие secrets не передаются аргументами и не коммитятся. Два profiles запускаются отдельно; credentials реальных пользователей не импортируются.

`test/mail-templates.test.ts` проверяет closed templates, fragment links, integer amounts, отсутствие внутренних notes, coarse devices и Moscow boundaries. `test/mail.test.ts` использует настоящий disposable PostgreSQL 18 и scoped runtime accounts: encryption/metadata, cross-realm denial, accepted delivery, backoff/exhaustion/retry, stale invitations/reset, concurrency, crash/unknown, allowlist, reminder dedupe/end changes и реально запущенный pg-boss worker. Security suite дополнена TOTP/resend/audit/idempotency; real HTTP/browser desktop/mobile journeys читают секреты из **доставленного sandbox content**, а не исходного outbox. В них проверяется также раздел «Письма».

## Что остаётся

Postbox API/SMTP adapter и provider outcome reconciliation/webhooks, доменная настройка SPF/DKIM/DMARC, реальная доставляемость/ретенция, отправитель и support inbox, actual provider outage/monitoring/heartbeat, cleanup и retention, bounded reminder scanning/pagination, другиe timezone/DST, real Safari/iPhone, maintenance/email-change/admin-email-override события (их продуктовые actions ещё не реализованы), owner onboarding и полная release acceptance. Все затронутые требования остаются **partial**. Staging/Production, услуги и объединение с main здесь не выполняются.

Официальная основа: [pg-boss constructor](https://pgboss.io/api/constructor), [jobs](https://pgboss.io/api/jobs), [queues](https://pgboss.io/api/queues), [Yandex Postbox send-email](https://yandex.cloud/ru/docs/postbox/operations/send-email). Точная queue API и construction plan проверяются также по установленному pinned package; наличие adapter interface не доказывает интеграцию Postbox.
