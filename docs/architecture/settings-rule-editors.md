# Структурные настройки и персональные правила

Рабочий блок `feature/settings-rule-editors` поверх PR №29, `64b5ea1718c717cee7cea0f71421962cad158e99`.

Основание: Master Specification 11–16, 31, 34, 49, 51–52; согласованные B-01/B-03/B-07/B-09. Исходные PDF/Word и baseline не меняются. Блок не закрывает всю спецификацию Settings или Rules.

## Подключённый интерфейс

- Счета: объединение в выбранную каноническую карточку; разделение с созданием до девяти новых карточек, их типом, видимостью, участием в аналитике и кредитной моделью. Все сохранённые экземпляры источников, псевдонимы и операции распределяются явно. Коррекцию операции можно сохранить на другом собственном счёте. Банковские оригиналы не меняются.
- Категории: объединение карточек одного уровня, перенос в другую ветку/корень, изменение допустимой роли и удаление с заменой или снятием назначения. Финансовые операции сохраняются. Для конфликтов пользователь задаёт роль операции/части и зависимых подкатегорий. Сервер проверяет полный результат, переносит зависимости и выключает неоднозначные правила.
- Контрагенты: регистрация/игнорирование обнаруженных предложений, отметка «Это я», объединение, разделение с полным явным распределением и обычное удаление карточки. При разделении источники и их банковский псевдоним должны получить одинаковую карточку. Обычное удаление не удаляет финансовые операции.
- Правила: создание, редактирование всех поддержанных ядром условий AND/назначений, приоритета, включение/выключение, список соответствующих прошлых операций, удаление и отдельное применение к прошлым операциям. Поддержанный scope: merchant equals/contains, sanitized description contains, account/bank/counterparty, direction/kind, signed integer-minor amount range, RUB. Recurring pattern не добавляется под видом поддержанного условия.

Редакторы фиксируют снимок workspace generation/revision при открытии, сохраняют черновик при внешнем обновлении и блокируют отправку до нового открытия. В preview/commit идут только типизированные закрытые intents и opaque IDs. UI показывает названия/порядковые номера; номера карт, последние цифры и HMAC не отображаются.

## Историческое применение правил

`apply_rules` принимает конкретный `ruleId` и уникальную фиксированную выборку 1–1000 operation IDs. Выбранное правило должно быть включено, готово и соответствовать каждой операции. Сервер проверяет принадлежность и активный entitlement в общей finance boundary как при preview, так и при commit. Проверяется вся выборка до первой записи.

Применяется весь актуальный набор включённых готовых правил, с существующими приоритетами конкретности и numeric priority. Подтверждённые вручную facets, надёжный банковский kind и явное inclusion защищены. Равные противоречивые назначения, включая inclusion, не выбирают произвольного победителя: сохраняется значение и добавляется `conflicting_rules`. Повторная явная классификация пересчитывает прежнюю причину conflicting_rules по всему актуальному набору, сохраняя прочие причины проверки. Несовместимость назначенной категории и итоговой роли блокирует всю команду.

Правила меняют семантические поля родительской операции и inclusion; source observations, corrections, отдельные components и links не переписываются. Результат пересчитывается общим графом. Preview показывает точную выборку, изменяемые записи, защищённые решения, конфликты и totals. Новые операции не расширяют selection; импорт/редактирование после preview делает commit устаревшим. Все изменения группируются одним action ID, точный повтор commit идемпотентен, object-version History позволяет атомарный Undo без перезаписи новых решений.

`delete_rule` удаляет только настройку будущей классификации. Прошлые операции и provenance с rule ID сохраняются; preview показывает их число. Удаление восстанавливается через существующую object-version History. Новая миграция не требуется: используются таблицы/история миграций 0001–0016.

## Проверки и ограничения

Pure test проверяет равные конфликты inclusion и защиту явного решения. Шесть PostgreSQL/HTTP scenarios проверяют future-only edit, read-only preview, fixed IDs, tenant ownership, disabled/invalid scopes, full priority set, concurrency/access refusal, сохранность bank facts, History/Undo и удаление rules. Восемь UI scenarios запускаются на desktop/mobile; два дополнительных браузерных journeys работают через реальный HTTP/PostgreSQL, включая создание правила, прошлую выборку, отмену/Undo, удаление правила и объединение счетов. После двух отказов Docker Hub на загрузке service container CI получает тот же Docker Official Image PostgreSQL 18.4 через публичное зеркало ECR; version, PostgreSQL проверки и весь набор тестов сохраняются. Документация Docker подтверждает зеркало: https://www.docker.com/blog/news-from-aws-reinvent-docker-official-images-on-amazon-ecr-public/. Полный CI и точный commit фиксируются в PR после завершения.

Полные counterparty карточки со статистикой/first-last seen, полноценные import labels для различения старых экземпляров/aliases, recurring patterns, AI/NL предложения, создание правил из массовой правки, глубокое физическое удаление/reset в UI, budgets/views/widgets и будущие module dependencies остаются открыты. Большие split/category формы пока используют обычные списки без виртуализации. Production не выпускается: требуются owner Staging acceptance, инфраструктура, security/provider checks, artifact/migration/rollback review.
