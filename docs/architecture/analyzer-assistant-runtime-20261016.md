# Подключение нового помощника к HTTP и PostgreSQL

Реализован отдельный opt-in путь изолированной приёмки. Он использует
тот же `runAssistant`, что и синтетические языковые испытания, и существующий
серверный расчёт операций. По умолчанию помощник не включён. Для test configuration используется явно заданный подставной HTTP transport.
Для Staging реализован отдельный провайдер: приватный systemd credential,
список допущенных пользователей, проверка модели через GET и срок действия
настроек. Перед каждым POST транзакционно проверяются оставшиеся вызовы
и бюджет; прежние подтверждённые расходы переносятся без обнуления. Это не включение модели на Staging
или Production и не подтверждение готовности всей спецификации продукта.

## Серверный маршрут

При явном включении провайдера существующие `/finance/analyzer-task`,
контекст фильтров, отмена, история и действия чата обслуживают новый протокол.
Одновременная настройка нового и прежнего провайдера запрещена. Старый чат
остаётся читаемым; для отправки в новый протокол нужен новый диалог.
В control profile провайдер недоступен.

Запрос фиксирует пользователя из сессии, lifetime чата, generation данных,
revision фильтров/данных, подтверждённую задачу, число сообщений и календарь.
Доступ, отмена и актуальность повторно проверяются перед вызовами и
инструментами, после ожиданий и при атомарной записи ответа. Во время HTTP
нет открытой транзакции или блокировки финансового workspace. Отдельная
session advisory lock защищает только один request ID и освобождается при
смерти соединения. Короткие транзакции используют то же соединение:
запрос не ждёт второго слота и работает даже при pool size=1. Новый request в том же чате не обгоняет незавершённый.

Результат собирает существующий расчётный код: фильтры, integer minor units,
компоненты/связи, сравнение, ограниченный preview, зависимости удаления,
widget и действия «Как рассчитано» / «Открыть в Операциях» сохраняются.
Follow-up читает текущую БД, а старый ответ остаётся историческим снимком.
План модели не становится SQL или полномочием. Общий ответ и посторонний
вопрос не вызывают финансовые инструменты и не списывают единицу задачи.

## Календарь

`finance.assistant_profile` хранит выбранный IANA timezone независимо от
московского календаря коммерческого access cycle. Московского fallback
для нового помощника нет. Отсутствующая настройка останавливает dispatch.

При первом открытии UI предлагает системе часовой пояс браузера. Серверная
операция initialize сохраняет его только при отсутствии настройки: другое
устройство не перезаписывает уже выбранный пояс. В чате пояс виден и
редактируется. Смена пояса во время выполнения запрещает сохранение
устаревшего ответа. Date-only банковские факты не пересчитываются в instants.

## Хранение и стоимость

Аддитивная миграция `0027_assistant_runtime.sql` создаёт отдельные таблицы
профиля, диалога и private run receipt с FORCE RLS. Коммерческие шаги
`assistant_0..2` отделены от старых `gate`/`plan`. Старые квитанции и их
identity не переписываются. Исходный frozen executable binding сохранён.

Перед POST транзакционно сохраняются резерв стоимости и коммерческая
квитанция, затем private sent receipt. Фактический usage учитывается до
разбора ответа, даже при удалении чата или потере доступа. Неизвестный usage
оставляет резерв и запрещает новый платный dispatch; повтор не считается
бесплатным вызовом модели. Готовый request ID возвращает сохранённый ответ.
Цена не вычисляется с float money. Только успешный financial query списывает
единицу пользовательского лимита. Последняя единица проверяется под
серверной блокировкой перед dispatch и повторно перед записью результата.

Ответ, его зависимости, диалог, подтверждённый book, единица лимита и
завершение claim сохраняются атомарно. Подготовленный payload сначала
попадает в durable receipt, чтобы восстановление не требовало нового POST.
После удаления чата private receipts/context каскадно удаляются; технические
квитанции стоимости сохраняются. Поздний ответ не создаёт чат заново и не
оставляет лишнюю занятую единицу запроса. Deletion/reset/reference triggers
учитывают также неподтверждённый черновик категории.

## Проверка

Программные проверки отделены от независимых ответов реальной модели:

- PostgreSQL 18: HTTP, RLS, restart replay, quota/cost, актуальные коррекции,
  неизвестный usage, отмена/удаление, потеря доступа, revision/timezone,
  одновременные requests и один structural repair максимум.
- Chromium desktop/mobile: профиль Honolulu, ручные UI touches, потерянный
  ACK, повтор того же payload, межвкладочный CAS, reload/cancel и удаление
  только после подтверждения. Нет горизонтального переполнения и записи
  финансового диалога в browser storage.
- Существующие software checks помощника, расчётного ядра и старого HTTP/UI
  остаются отдельными регрессиями.

Установка реальных credentials на сервере, оплата запросов через веб-приложение,
применение миграции к развёрнутому стенду и продуктовая приёмка Staging
ещё не выполнены. Интернет-поиск и текущие внешние финансовые факты
по-прежнему требуют отдельного источника; недоступность поиска сообщается
пользователю без выдуманных цифр.

## Установка Staging и откат

После зелёных checks `scripts/prepare-assistant-staging.sh` собирает pinned commit
с locked dependencies от обычного deployment user. Root installer проверяет
изолированный PostgreSQL на loopback 5411, активный подтверждённый тестовый
аккаунт и единственный frontend root для test.cashneuro.ru. Адрес тестового
аккаунта вводится в серверном терминале и не выводится в отчёт.

Перед изменениями создаётся private backup БД и конфигурации. Миграции 24–27
применяются только для отсутствующего непрерывного хвоста, одной транзакцией.
Если у выбранного аккаунта вообще нет quota policy, добавляется тестовый лимит
20 задач; существующие квоты и entitlement не меняются. Общие лимиты реальных
вызовов и стоимости независимо ограничены остатком согласованного этапа.

Отдельный instance drop-in переключает только Finance API. Control и mail
продолжают использовать прежний release; общий backend-current не меняется.
Приватные credentials копируются в принадлежащий DynamicUser runtime directory
с правами 0600 привилегированным ExecStartPre. Frontend root заменяется только
для тестового сайта; Caddy candidate проходит validate до переключения.

Ошибка переключения вызывает автоматический откат файлов/API/frontend. Команда
ручного отката печатается до переключения и в итоговом JSON. Аддитивные таблицы,
технические квитанции стоимости и тестовая quota policy сохраняются; откат
кода не стирает новые данные и не восстанавливает старую БД поверх новых действий.
Установщик не отправляет model completion. Первый запрос выполняет сам владелец
в новом диалоге сайта, используя только синтетические финансовые данные.
