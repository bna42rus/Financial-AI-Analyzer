# Единый справочник организаций и правил распознавания

## Утверждённый порядок работы — 25.10.2026

С этого момента сначала совместная проработка полного справочника, затем реализация и общий запуск проверок. Продуктовые магазины — явное исключение: владелец поручил закончить уже начатую реализацию и её проверки сейчас. Остальные категории не реализуются по одной сразу после обсуждения.

Для каждой категории последовательно, отдельным сообщением:

1. Определить направление деятельности, подходящие категории пользователя, список организаций и конкретных сервисов. Москва подробно; по России — крупные и средние региональные сети. Публичный источник и дата проверки для каждой записи.
2. Проработать написания: исходное имя, кириллица/латиница, падежи и словоформы, транслитерация, смешанные алфавиты, пробелы/дефисы/слитное написание, допустимые сокращения и значимые цифры. Общий словарь «слово → деятельность» согласуется отдельно, не подменяется перечнем брендов.
3. Разобрать надёжность на примерах: когда допустимо автоматическое назначение; когда нужно предложение с проверкой; когда нужны дополнительные признаки; когда назначать нельзя. Confidence не является измеренной вероятностью.
4. Исключить пересечения с другими брендами, товарами, обычными словами и категориями. Проверить подразделения и разные услуги одного бренда; платёжный посредник/юридическое лицо не доказывают конечного продавца. Неподтверждённые aliases не объявлять фактическими банковскими обозначениями.
5. Подготовить случаи будущей проверки с ожидаемым результатом и объяснением: положительные, отрицательные, неоднозначные, конфликтующие. Это проектирование проверок и ручной разбор, не запуск полной автоматизации.
6. Показать полный раздел владельцу, внести его поправки и закрепить согласованную версию. Перейти к следующей категории.
7. После всех категорий свести разделы в этом документе, проверить общие конфликты и только затем реализовать согласованный набор и запустить общий автоматизированный прогон. Платный модельный прогон отделяется от программных проверок и не повторяет уже оплаченные ответы без причины.

## Согласованное уточнение: предварительная категория при сомнениях — 25.10.2026, дополнено 26.10.2026

Владелец уточнил общий подход во время проработки транспорта: при наличии обоснованной гипотезы ставить предварительную категорию с видимой пометкой **«Стоит проверить»**, а не оставлять операцию без предложения только из-за того, что точная услуга/корзина ещё не установлена. Правило применяется ко всему справочнику, включая ранее согласованные разделы; в части отказа из-за одной только неполноты сведений это уточнение имеет приоритет. Это спецификация будущей общей реализации, работающий код этим документом не меняется.

1. Уточнение владельца от 26.10.2026: однозначно узнанный сервис с очевидным профилем достаточен для обычной категории без «Стоит проверить». Подробного описания услуги в выписке не ожидаем и не требуем; его отсутствие само по себе не создаёт сомнение в категории. Например, Делимобиль/Яндекс Драйв/Ситидрайв/BelkaCar → Каршеринг без Review категории. Точное содержимое чека, маршрут и вид поездки для этого не нужны. Если же именно категория реально неоднозначна (несколько существенно разных направлений сервиса, конфликтующие признаки или недостаточно надёжная идентичность), существующая подходящая категория предварительно ставится в пользовательском отображении с пометкой «Стоит проверить» (Review); это не пустое предложение категории только в отдельном диалоге. Не блокировать импорт или требовать ответа пользователя перед таким предварительным распределением.
2. Конкретно **Яндекс Заправки → категория заправок/топлива пользователя + «Стоит проверить»**, когда услуга не уточнена. Для текущего базового каталога это «Транспорт → Топливо», без обязательного переименования пользовательской категории. Если прямо указана мойка, зарядка, эвакуатор или дорога, учитывать конкретные сведения, не перекрывать их профилем топлива.
3. Конкретно **Парковки России → категория парковок пользователя + «Стоит проверить»**, когда смысл списания не уточнён. В текущем базовом каталоге есть «Транспорт → Парковки и дороги»; это не разрешение создать/переименовать категорию. Если прямо установлен штраф, возврат или иной вид события, сохранить его и применить конкретное назначение.
4. Дополнение владельца от 26.10.2026: **Яндекс Go / Яндекс Го / Yandex Go / YandexGo без уточнения услуги → Такси + «Стоит проверить»** для подходящей операции оплаты сервиса, если нет прямых сведений о другой услуге и более приоритетного пользовательского решения. Это согласованный предварительный профиль, а не доказанный факт поездки. Прямое указание самоката/велосипеда, доставки, еды или иной услуги имеет приоритет; финансовый вид возврата/перевода/холда не меняется. Если подходящей категории нет, действует правило доступности категорий, без молчаливой замены на общественный транспорт. Общее слово «Яндекс» без Go/конкретного сервиса не получает автоматически тот же профиль.

Для остальных сервисов — тот же принцип: очевидная категория по однозначному профилю назначается без Review; при реальном сомнении ставится разумная предварительная категория с пометкой вместо отказа. Если известен лишь родительский раздел, допустимо предварительно поставить его, не придумывая подкатегорию, точный бренд, состав чека или способ получения. Дефолтные профили остальных многосервисных агрегаторов определяются в соответствующих разделах, не изобретаются скрыто при внедрении.
5. Отсутствие оснований вообще, несколько равносильных противоположных трактовок, сильное неразрешимое противоречие, ложное совпадение обычного слова/чужого бренда не дают основания произвольной категории. В таком случае сохраняются проверка/уточнение без вымышленного назначения; независимо установленное более широкое направление может быть предварительно указано.
6. Пометка видна рядом с категорией; причина сомнения доступна пользователю понятными словами, например «Через этот сервис оплачивают разные автомобильные услуги; предполагаем заправку». Не показывать технические коды/версию промпта как объяснение. Пользователь может подтвердить или изменить категорию. Предварительное распределение не считается ручным подтверждением и не создаёт личное правило для будущих покупок.
7. Сохраняются более приоритетные ручные решения/личные правила, ограничения доступных видимых категорий и принадлежность операции пользователю. Нельзя заменить отсутствующее «Такси» на «Общественный транспорт» молча, восстановить удалённую категорию или перезаписать компоненты ради предварительного профиля.
8. Дата, сумма, вид события, банковские факты/имя/алфавит, идентичность/HMAC, связи и повторный импорт сохраняются. Предварительная категория относится к пользовательскому аналитическому слою. Текущая продуктовая модель учёта и фильтров Review сохраняется; не исключать такую операцию из суммы и не учитывать её второй раз из-за самой пометки. Старые подтверждённые решения массово не переклассифицируются.

Будущие проверки всех разделов должны различать: назначенную предварительную категорию, видимую пометку, причину Review и отсутствие пользовательского подтверждения. Отдельно проверяются подтверждение/исправление пользователем, защита личных решений и все ситуации без достаточного основания. Число confidence модели не отменяет Review и не заменяет профиль/признаки. Для дополнения от 26.10.2026 обязательно проверить три разных входа: (а) оплата Яндекс Go без уточнения → Такси + Review; (б) Яндекс Go с прямо указанным самокатом/доставкой/едой → конкретное направление, без профиля такси; (в) только Яндекс без сервиса → не подставлять такси. Это проект ожидаемых результатов, не выполненный прогон.

Дополнение для всех разделов: **отсутствие расшифровки услуги не равно неоднозначности категории**. Для однозначно узнанного каршеринга, кафе/ресторана, продуктовой сети, АЗС, автосервиса, мойки, транспортного перевозчика или зарядного сервиса очевидный согласованный профиль применяется без Review категории. Сомнение в роли, возврате, связи или дубле хранится отдельной причиной и не делает категорию спорной автоматически. Согласованные специальные предварительные профили Яндекс Go → Такси, Яндекс Заправки → Топливо, Парковки России → парковки сохраняют «Стоит проверить» из-за реальной многосервисности. Это уточнение имеет приоритет над прежними формулировками, где одна только неизвестная детализация требовала Review.

## Обязательные проверки из приложенных скриншотов

- Падежи («в Пятёрочке»), кириллица/латиница («Ashan», «Lenta»), регистр, ё/е, смешанные алфавиты.
- Границы слов, чужие приставки/суффиксы, числовые хвосты торговых точек: узнавать магазин, не совпадать внутри другого слова.
- Омонимы «Победа», «Линия», «Европа», короткие ДА/В1: без нужных дополнительных признаков категория не назначается.
- Кафе, аптека, одежда и другая деятельность не получают «Продукты» из-за совпадения бренда.
- Те же ограничения действуют на ответ модели: высокая уверенность модели не заменяет банковского подтверждения. Прежний кэш не выдаётся за проверенный новой политикой.
- Банковские факты, ручные/подтверждённые исправления, личные правила, разделённые покупки, деньги, идентичность, повторный импорт и итоги сохраняются.

## Поведение

- Явные падежи и три ограниченных способа транслитерации; регистр, ё/е, разделители, слитное написание составных имён и смешанные кириллица/латиница только по закрытому списку. Это кандидаты распознавания, не реальные банковские образцы. Нельзя обещать все возможные написания или нулевую неоднозначность по одному тексту.
- Полные границы слов: SPAR349 допускается, SPARK, LENTA349X и чужие приставки/суффиксы отвергаются. Нет нечёткого сопоставления брендов по расстоянию редактирования.
- Для омонимов необходим явный признак магазина или продуктовый MCC. «Покупка», город и номер точки не доказывают деятельность. Конкретные METRO CASH & CARRY и Гиперглобус различаются от общих METRO/Глобус. Короткие ДА/В1 не достаточны.
- Указание иной деятельности или противоречащий MCC запрещают правило продуктов. Неподтверждённое назначение модели также отклоняется; категория остаётся на проверке. Это не доказательство, что ошиблась модель, если исходного контекста недостаточно.
- Разные бренды в одной строке не выбираются по первому совпадению; конкретное подразделение уже известного бренда сохраняет приоритет.
- Пользовательские категории не создаются/переименовываются этой доработкой. Личные и подтверждённые решения, компоненты, деньги, даты, счета, исходная строка, HMAC, dedupe и связи не изменяются. Без нужной видимой расходной категории назначения нет.
- Исторические пользовательские решения не переписываются автоматически. Новые варианты применяются при очередной допустимой обработке импорта/классификации.
- Алфавит исходного названия сохраняется; исключение TimeWeb из прежнего решения остаётся. Имена в этом документе — идентичность бренда, а не требование транслитерировать отображаемое название.
- Версии: merchant-catalog/2 и category-service-evidence/3. Изменение policy входит в подпись кэша; старые решения не выдаются за проверенные новой политикой.
- Основание: master_spec_v1.pdf, разделы 13–14 (категории), 16–17 (приоритет/уверенность), неизменяемые банковские факты и компоненты.

Всего записей продуктового блока: **50**; буквальных вариантов: **756**. Общий справочник: **105** записей. Нормализованные дубли внутри одного бренда допустимы, между разными брендами тест запрещает.

Общие ограничения для всех P01–P14:

1. Ручная/подтверждённая категория и подходящее личное правило сильнее глобального справочника. Не переписывать старые решения или компоненты ради нового словаря. Удалённые/скрытые пользовательские категории не восстанавливаются автоматически. Если подходящей подкатегории нет, допустима однозначная существующая родительская категория; произвольную замену не подбирать.
2. Полные имена и ограничения F01–F61 обязательны. Границы слов, существенные цифры, исторический период, конкретный сервис/подразделение сохраняются. Нельзя исправить ЦЕХ86 в ЦЕХ85, выбрать кофейню по OnePlus или сеть Ё по букве Е. Отрицание, упоминание товара и цитата не являются покупкой у организации.
3. Два независимых продавца в одной строке — конфликт, а не выбор первого. Подтверждённая связка агрегатор + ресторан — роли одного заказа, а не конфликт. Конкретная услуга или товар сильнее общего профиля бренда.
4. Ресторанный MCC может поддержать деятельность, но не устанавливает сеть, доставку, блюда и доли суммы. Признаки магазина/оборудования/перевода требуют отдельного разбора. Неподтверждённые сведения из пользовательского свободного комментария не превращаются в банковский факт и не направляются модели.
5. Один платёж за еду, доставку, упаковку и чаевые не дробится по догадке. Отдельная подтверждённая операция чаевых/курьерской услуги не объявляется стоимостью еды; подходящая категория требует собственного основания или решения пользователя. Подписка на скидки агрегатора не является заказом еды; абонемент на подтверждённые готовые рационы рассматривается как питание.
6. Ручное распределение покупки использует существующие компоненты: сумма частей точно равна сумме покупки, без одновременного учёта полного родителя. На следующую покупку того же бренда доли не переносятся; повторный импорт сохраняет связь и ранее подтверждённые части.
7. Возврат не превращается в новый расход. Сохраняются вид события и установленная связь с покупкой/частью; без связи пропорции не угадываются по бренду.
8. Банковские факты, исходное имя и алфавит, описание, сумма, дата, счёт, идентичность/HMAC, dedupe и связи не меняются. Защищённые реквизиты/ссылки не восстанавливаются для узнавания бренда. Никакой массовой переклассификации истории этим документом не запускается.
9. Правила одинаково ограничивают локальный справочник, модель и кэш. Высокая уверенность ответа не обходит неоднозначность; старый кэш не выдаётся за прошедший новую политику.

Политика согласована владельцем, включая начальную категорию пекарен «Еда вне дома» и категорию «Продукты» для пищевого вендинга; по уточнению от 26.10.2026 очевидная категория не требует Review только из-за отсутствия детализации услуги/чека. #### Финансовые и пользовательские ограничения для U01–U22

1. Категория и финансовый смысл независимы. По PDF 9.2/9.7 обычный перевод человеку без надёжного контекста остаётся unresolved по роли; слово Такси в имени не делает его покупкой. Категория может быть предварительной, не изменяя защищённый kind/role. Разрешённые изменения facets следуют существующему серверному контракту, а не свободному решению модели.
2. Пополнение транспортной карты/сервисного баланса не называется доказанной поездкой. Справочник сам не создаёт кошелёк, виртуальный счёт, списание или связь own_transfer. Если загружены обе стороны движения собственных средств, применяются существующие подтверждённые связи; одна сумма не учитывается повторно как пополнение и поездка. Если кошелёк не представлен как собственный счёт, нельзя молча объявить любой банковский платёж neutral только из-за слова пополнение: сохраняется текущая продуктовая модель фактической операции и Review при неясности роли.
3. Предавторизация/временная блокировка не создаёт новую завершённую покупку; источник статуса учитывается, не выдумывается по бренду. Обеспечительный платёж/залог, окончательная аренда, удержание и возврат различаются по доступным фактам и существующим kind/role/links. При недостатке сведений спорная роль остаётся на проверке; слово залог не является разрешением молча скрыть фактическое списание или переписать bank facts. Новый тип финансового события/жизненный цикл холдов этим документом не вводится.
4. Один платёж с поездкой, топливом, платной дорогой, страховкой, комиссией и иными частями не делится по догадке. При наличии точного подтверждённого состава применяется существующий механизм компонентов с точной суммой; полная родительская transaction не суммируется с частями. Банковская комиссия, прямо выделенная отдельной услугой/частью, не объявляется стоимостью самой поездки по одному бренду; учитывается по своей природе.
5. Возврат уменьшает связанный расход в своей фактической дате, а не меняет дату покупки или создаёт новый доход (PDF 9.3/9.8). Доступные allocations/capacity и выбранные пользователем части сохраняются. Без подтверждённой связи не угадывать исходную поездку/маршрут/доли по совпадению бренда или суммы. Переклассификация не создаёт автоматическую связь и не смягчает dedupe.
6. Ручные подтверждения, подходящие личные правила и существующие компоненты сильнее профиля справочника. Подтверждение категории снимает только её причину проверки; возможный дубль/несвязанный возврат/спорная роль могут продолжать требовать внимания (PDF 10/17.4). Предварительное назначение не считается подтверждением пользователя или обученным личным правилом. Никакой массовой перезаписи истории.
7. Использовать существующие подходящие видимые категории пользователя с серверной проверкой принадлежности. Отсутствующие/скрытые/удалённые категории не создавать/не восстанавливать молча, из одноимённых вариантов не выбирать случайно. Если Такси отсутствует, нельзя автоматически заменить его на Общественный транспорт; объяснить отсутствие и предложить варианты пользователю. Однозначный доступный родитель Транспорт может быть предварительным назначением по общему правилу, без выдачи чужой подкатегории за выбранную.
8. Многосервисные и исторические имена обрабатываются по R01–R67. Не определять точный сервис/маршрут/продавца по платформе, короткому слову, городу, номеру точки или одному MCC. Конкретный непротиворечивый товар/услуга сильнее стартового профиля; слабый MCC не отменяет прямые факты. Высокая confidence модели не снимает пометку и не разрешает конфликтное назначение. Число уверенности не объявляется измеренной вероятностью.

#### Принятое уточнение к U01–U22: Review по реальной причине

Для будущих проверок обязательно различить: (1) сервис однозначно узнан, профиль очевиден, описания услуги нет → обычная категория без её Review; (2) конкретная категория реально неоднозначна → предварительная категория + «Стоит проверить»; (3) категория очевидна, но есть независимый дубль/несвязанный возврат/спорная роль → категория не становится сомнительной автоматически, сохраняется только соответствующая причина внимания; (4) три специально согласованных многосервисных профиля Яндекс Go/Яндекс Заправки/Парковки России сохраняют Review при отсутствии конкретизации.
