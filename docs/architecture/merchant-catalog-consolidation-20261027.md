## 1. Как читать сводку и какой текст имеет приоритет

1. PDF v1.3/source-manifest и approved overrides остаются основой. Ручное решение/verified, специфическое личное правило, общее личное правило имеют приоритет над общим каталогом в предусмотренных моделью границах.
2. В [master](./merchant-catalog-master-20261025.md) остаются общая Review-политика, старые блоки и исходные нумерации. Дополнительные NET/DIG/BEA и полные MP/ENT/EDU/TRV/PET/GFT/FIN дополняют его; нельзя ориентироваться только на старый последний абзац «следующий шаг».
3. **APPROVED** — в доступном контексте/документе есть запись принятия показанного объёма. **APPROVED_BASELINE** — прежний продуктовый исключительный этап описан источником; здесь его выполнение не перепроверялось. **PARTIAL_RECORD** — части/проекты есть, но единая финальная запись неоднозначна. Это **не утверждение, что владелец никогда их не согласовывал**, и не отмена известных принятых решений.
4. Поиск дополнительных прежних согласований через Personal Context недоступен. Не присваивать пяти старым участкам фиктивные дату/цитату одобрения; не просить пользователя заново составлять списки. Сохранить готовые материалы и отдельно показать пакет фиксации ниже.
5. Источник SRC/IDX/REG, PEND, INT, HIST, REF описывает иное измерение, чем одобрение проекта. Согласование не закрывает источник, исторический период, неизвестный платёжный alias или пригодность международной оплаты из РФ. Источники заново не проверялись этим аудитом.
6. Реализация ≠ запись правил ≠ выполнение теста ≠ Staging-релиз ≠ приёмка владельца. Частичную старую реализацию продуктов/split нельзя выдавать за готовность нового каталога.

## 7. Общие критерии будущей реализации и проверки

Это требования к будущему единому прогону, не новые результаты тестов и не число платных вызовов.

1. Трассировка: исходный файл/профиль/форма/U/C/T, версия каталога/схемы/Registry/cache, синтетические input/expected, отдельные actual/raw/validator/compiler/core/UI/access и причина расхождения.
2. Приоритеты: manual/verified/specific/broad personal/global/AI/bank по PDF; обновление общего словаря не перетирает личное решение и не создаёт личное правило из предположения.
3. Очевидный профиль без лишнего category Review; обоснованная предварительная категория видна в операции с причиной и не становится verified. Нет оснований — не произвольный fallback.
4. Яндекс Go → Такси + Review, Яндекс Заправки → Топливо + Review, Парковки России → парковки + Review в согласованных исходных условиях. Прямые признаки другой услуги выше профиля; корень Яндекс не то же самое.
5. Source/user/effective, merchant/display/counterparty/channel/account различны. Все исходные даты/суммы/идентичности/HMAC/dedupe/parts/links защищены от косметического переименования.
6. Никакого глобального wildcard/fuzzy/stemming для всех похожих букв/падежей. Проверяемый closed inventory, word boundaries, омонимы/числовые хвосты/ложные приставки/смешанные символы/контекстные отрицания.
7. RUB-only, integer minor, точные parts/allocations, components вместо parent; 50/51/остаток/переполнение/валюта. Факт классификации не создаёт новую банковскую строку/виртуальный счёт.
8. Кредитка repayment neutral и completeness banner; ordinary Cashflow/Economic и account override по PDF; неизвестный состав кредита/BNPL не выдумывается.
9. Refund/reversal/compensation/own/private/debt transfer/cashback различимы, ограничения связей/частей сохраняются. Actual parent после ошибки, не подстановка golden контекста.
10. Bank date source-local, пользовательский today/relative period и UI timestamps через профиль; поездка не сдвигает факт выписки. Проверить FIN-I01, не менять слепо всё на Москву или profile zone.
11. Повторный импорт той же строки сохраняет ручные parts/поля; другая новая покупка того же продавца не наследует проценты распределения автоматически. Отмена перекрывающихся импортов/Undo/удаление не возвращают старый неверный source.
12. Приватность по принятому требованию: ФИО, обычные цифры/словесные переводы не blanket-mask. Номера карт/счетов/договоров/телефоны/email/паспорт, маркированные реквизиты/коды/ИНН/БИК и URL остаются закрыты; HMAC не доступен AI и не восстанавливается.
13. Ownership/status/entitlement/RLS/deletion/revision до preview и снова commit, серверная authority; Registry закрыт. User data/keys/secrets/admin/sessions/password/SQL не модели.
14. Операции/Review/карточка/поиск/фильтры/Обзор/Бюджеты/Analyzer/экспорт дают один результат при одинаковых условиях; явный запрос выше UI-контекста, same filters/roles/parts/net/gross/RUB.
15. Existing fixtures не переписываются ради PASS; ошибочный ответ модели сохраняется. Успех защитного отказа не превращается в правильное понимание моделью.
16. Платные вызовы после структурных/локальных проверок и утверждённого scope; действующие лимиты/admission/tariff/usage/reconciliation, прошлые расходы не сбрасываются. Нет автоматического повтора неопределённого POST.
17. PASS/FAIL/BLOCKED/NOT_RUN по слоям и входам; исключённый PEND с причиной не маскирует провал активного профиля. Нельзя выдать исторический replay за свежий замер.
18. После готового artifact: полный требуемый CI, резервная копия/аддитивные миграции/rollback или forward fix, health/UI/import worker, конкретная Staging-приёмка владельца. Согласованный документ не Production-разрешение.

## 8. Очередь без повторного заполнения тех же списков

1. **Этот шаг:** FIN принят, корпус сведён, покрытие/дубли/старые статусы/пробелы обозначены; структурная проверка, без runtime-вызовов.
2. **Следующий содержательный шаг:** отдельный подробный ACT «слово → деятельность» по всему принятому дереву, с первой полной таблицей терминов/форм/условий/коллизий. Не ограничиться кафе/аптекой и не смешивать его с написаниями 1000 брендов. Формы `optika`, `apтека`, `кафе/cafe/kafe`, `столовая/stolovaya`, `вендинг/vending` обязательны; общий wildcard запрещён.
3. Затем NAME: понятные имена операций на исходном/согласованном языке, TimeWeb, безопасные хвосты и защита значимых цифр/сервисов. Готовую безопасную часть не отменять.
4. На общем финальном контракте закрыть запись пяти старых участков, scope бизнеса/инвестиций/страхования, выбрать активные источники и явные исключения PEND, concrete rollout новых узлов. Это не требование заново переписать все разделы.
5. Только затем общая реализация, локальные проверки/отобранный модельный прогон/показ ошибок/конкретный Staging-релиз. Не откладывать бесконечно из-за необязательного выключенного PEND; не обходить незакрытую финансовую/приватную/серверную модель.

Структурная проверка текущего сведения: точность исходных 28 Git blobs, 20 строк покрытия, сохранение обоих HOME-планов и 32 связей, 16 межраздельных связок, 12 открытых задач, локальные file-target ссылки и непрерывные ID FIN/NOT_RUN; `git diff --check`. Обновление заголовков/согласования FIN не изменяет ни одной исходной таблицы aliases/U/C/T или продуктового кода. В полном корпусе каждый из 23 исходных документов сохранён целиком с актуальными служебными пометками; содержимое/длина/SHA256 сверены с текущими исходниками. Генерация не выбирает между конфликтующими проектами и не меняет старые оракулы. Машинный индекс не тестовый отчёт и не runtime-каталог.
