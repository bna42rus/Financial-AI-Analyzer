# Обслуживание диска и резервные копии CashNeuro

Основание: запрос владельца 23.11.2026; PDF §44, §51; существующее разделение
Staging/Production и KMS realms. Код инструментов устанавливается отдельно от
работающего API. Установка не переключает релиз приложения, провайдера ИИ,
тариф Timeweb, лимиты ИИ или доступ пользователей.

## Что делает первая команда

1. Устанавливает конкретный Git commit в root-owned каталог инструментов.
2. Удаляет неиспользуемые старые backend-релизы. Сохраняет действующий релиз,
   две его предшествующие версии, все версии по ссылкам, конфигурациям служб,
   Caddy, процессам, mounts и зависимостям; новые подготовленные кандидаты тоже
   сохраняются. Поэтому при старом `backend-current` могут временно оставаться
   четыре и более версии. Саму ссылку инструмент не переключает.
3. Показывает расположение Docker-томов, размеры обеих БД и крупнейших таблиц.
4. Сверяет зависшие запросы Staging. По уже записанному provider usage вызывает
   существующий `reconcileRecordedAssistantCosts` из проверенного исходного
   кода, сохраняя исходные цены, периоды и бюджеты. Usage `unknown` не списывается
   и не освобождается автоматически; модельные запросы не повторяются.
5. Проверяет ранее установленный ключ Cloud.ru на заведомо неполном запросе к
   completion endpoint без inference. Выбора другого провайдера и ввода нового
   ключа нет. Секреты, ответы провайдера и вопросы пользователя не печатаются.
6. Запрашивает приватные настройки существующего S3 и пароль архивов через
   `/dev/tty`. Создаёт первые копии и проверяет фактическое восстановление обеих
   баз в отдельных временных контейнерах без сети и внешних портов.
7. Включает расписания после успешных первых копий/восстановлений. Измеряет
   синтетическую модель на 5000 операций и 500 запросов Анализатора, затем
   выводит состояние и HTTP health обеих API.

Эта команда выполняется владельцем на сервере. Локальные unit-тесты не являются
подтверждением наличия объектов в его бакете или успешного восстановления его БД.

## Состав копии

| Объект | Содержание |
| --- | --- |
| `database.dump` | Согласованный custom-format `pg_dump` выбранной БД |
| `roles.sql` | Global roles/settings для аварийного восстановления; содержит чувствительные данные и хранится только в зашифрованном репозитории |
| `configuration/` | Caddyfile, env-файлы выбранной среды, systemd units/drop-ins, настройки ИИ/почты выбранной среды, KMS wrapping records |
| `manifest.json` | Среда, БД, время, размеры/хеши файлов, пути установленных релизов, крупнейшие таблицы |

RSA authorized-key.json KMS, сами KMS master keys, пароль резервных архивов и
S3 credentials не добавляются в архив. KMS-доступ восстанавливается отдельно
через учётную запись Yandex Cloud. Пароль архивов владелец хранит вне сервера.
Без исходных wrapping records и действующего KMS-доступа чтение защищённых
данных после восстановления не гарантируется.

В копию не входят ОС, Docker volumes целиком, node_modules, backend-релизы,
временные файлы или оригиналы банковских выписок. Исходные выписки не начинают
загружаться на сервер/S3 вследствие установки этих инструментов.

## Хранилище и сроки

Endpoint фиксирован: `https://s3.twcstorage.ru`. Приватный бакет выбирает владелец.
По решению владельца 24.11.2026 локальное ограничение ёмкости удалено.
Прежнее поле `quotaBytes`, включая сохранённое значение 1 ГБ, игнорируется.
Инструмент не вызывает API покупки/автомасштабирования и не меняет тариф;
при уже включённом авторасширении загрузки могут увеличивать объём/стоимость S3.

Restic создаёт отдельные зашифрованные репозитории:

- `cashneuro-backups-v1/production`: 7 последних ежедневных копий плюс 2 копии
  перед обновлениями, если оператор вызывает этот режим для Production.
- `cashneuro-backups-v1/staging`: 2 последние копии перед обновлениями.
- `cashneuro-backups-v1/production-deletion-journal` и соответствующий Staging
  repository: 2 последние накопительные выгрузки реестра.

Ротация удаляет старые snapshots/неиспользуемые блоки только после появления
нового проверенного снимка. Ошибка выгрузки или чтения манифеста оставляет старые
копии. Restic шифрует и дедуплицирует данные; экономия между сжатыми pg_dump
не гарантируется. Локального условия, останавливающего загрузку при 1/10 ГБ,
больше нет. Фактический отказ S3 в записи всё ещё завершает backup ошибкой,
сохраняя прежние snapshots. Versioning бакета может сохранять удалённые
версии объектов и увеличивать счёт; его настройки нужно проверить отдельно.

После ручной/ежедневной backup-команды и ежечасно watchdog измеряет сумму размеров
всех текущих объектов бакета через read-only ListObjectsV2 с AWS SigV4. Учитываются
все страницы (до 100 тысяч объектов/30 секунд), включая encrypted packs, metadata
и файлы вне backup-prefix. Имена объектов, continuation tokens и подписи не
выводятся. Предыдущие версии объектов и незавершённые multipart uploads не входят
в замер; это не строгий счётчик тарифицируемого объёма.

Ориентир уведомлений `capacityWarningBytes` по умолчанию 10 ГБ. Письма приходят
при 8/9/10 ГБ; при переходе на следующий уровень уведомление допускается сразу,
при сохранении уровня — не чаще раза в сутки. SMTP failure повторяется не чаще
раза в час и не подавляет отдельные аварийные backup alerts. Поломка замера/почты
отмечается отдельно и не превращает успешную копию в ошибку. После 10 ГБ backup
продолжается. Данные замера/доставки видны в `cashneuro-ops capacity` и `status`.
Доступный Timeweb объём и правила авторасширения по-прежнему задаются в панели.

`--update-tools-only` устанавливает новый пакет и запускает замер/status без
повторной очистки релизов, ввода секретов, выгрузки БД, restore или benchmark.

После подтверждённой S3-копии Staging локально сохраняются только 2 последних
`database.dump` известных staging-установщиков в `/var/lib/cashneuro`. Остальные
файлы этих каталогов, включая rollback metadata и cost/key audit, сохраняются.

## Расписание и уведомления

- Production backup: ежедневно 03:10 по Москве, RPO до 24 часов при исправном
  расписании; пропущенные/ошибочные задания увеличивают этот интервал.
- Копия Staging: перед обновлением новым установщиком. Старые ветки со старым
  `update-staging-release.py` не получают hook автоматически: изменение должно
  входить в исходный код будущего релиза.
- Реестр удалений/поколений: каждые 5 минут.
- Проверка восстановления: Production 1-го, Staging 2-го числа, 04:10 по Москве.
- Watchdog: ежечасно; ошибка при Production backup старше 36 часов либо restore
  test старше 40 дней.
- Очистка релизов: после успешного обновления новым установщиком и ежедневно
  в 05:20 по Москве.

Ошибки направляются только на заданный владельцем email через существующий
Postbox SMTP. Письмо содержит код инцидента без содержимого БД/секретов. Не более
одного письма в сутки; потерянный SMTP response не вызывает немедленной повторной
отправки. При недоступной почте ошибка также остаётся в systemd journal/status.

Обновление/backup/очистка используют существующий deployment lock. При занятом
lock плановое задание пропускается, а ручная операция возвращает явный код.
Backup не блокирует обычные чтения/записи приложения на всё время копирования.

## Реестр удалений и восстановление

Реестр содержит внутренние IDs исполненных удалений аккаунтов и наблюдаемые
generations/key versions финансовых пространств; email и финансовые строки
в реестр не выгружаются. Старые записи объединяются с новой выгрузкой, поэтому
ротация двух снимков не стирает накопленную историю.

Это периодический экспорт, не синхронная запись вне сервера в транзакции каждого
удаления. Между удалением и ближайшим успешным экспортом существует промежуток
до 5 минут, который увеличивается при сбоях. Он не обеспечивает полный журнал
каждого частичного удаления отдельной операции. Полная crash-safe deletion replay
остаётся отдельным release gate перед реальными клиентами, а не объявляется
выполненной данным инструментом.

`restore-test` сверяет хеши файлов, восстанавливает данные через pg_restore в
контейнере с `--network none`, без портов и live volumes, показывает конфликты
с актуальным реестром и удаляет тестовый контейнер/данные в finally. Привилегии
и владельцы в этом тесте не воспроизводятся (`--no-owner --no-privileges`);
проверка доказывает читаемость и восстановление структуры/данных, но не полный
аварийный запуск приложения с его security boundaries.

Автоматического восстановления в рабочую БД и открытия доступа нет. Перед
аварийным запуском оператор обязан применить актуальные удаления, проверить
roles/RLS, KMS unlock, миграции, остановку автооплаты/писем, и только затем
подтвердить открытие доступа. `productionRestoreAuthorized=false` выводится
явно. Recovery пароль/S3-доступ нужно заранее сохранить вне исходного сервера.

## Команды после установки

```bash
sudo cashneuro-ops status
sudo cashneuro-ops configure --replace
sudo cashneuro-ops prune
sudo cashneuro-ops prune --apply
sudo cashneuro-ops storage
sudo cashneuro-ops diagnose --settle-recorded-usage
sudo cashneuro-ops probe-cloudru
sudo cashneuro-ops backup staging --kind predeploy
sudo cashneuro-ops backup production --kind daily
sudo cashneuro-ops restore-test production
sudo cashneuro-ops benchmark
```

`configure --replace` исправляет введённые настройки без изменения тарифа;
прежняя конфигурация сохраняется приватно в `ops.previous.json`. Пароль уже
созданных репозиториев следует сохранить прежним: ввод другого пароля не
перешифровывает существующие архивы.

Для запроса с неизвестным usage сначала сверяют биллинг провайдера. Команда
`resolve-hold UUID` только проверяет условия. Дополнительный флаг
`--confirm-provider-unbilled` — явное заявление владельца об отсутствии списания;
оно записывается в audit. Это не provider-issued квитанция с нулевыми токенами.
Setup и планировщик никогда не выставляют этот флаг.

24.11.2026 владелец явно подтвердил отсутствие списаний по прежним запросам.
Установщик принимает отдельный аргумент `--confirmed-unbilled-existing-holds`:
только с ним выполняется `resolve-confirmed-holds --confirm-provider-unbilled`.
Scope закрыт UUID/исходными суммами:

- `e6b054ec-e6fb-4ae4-88e4-27a626159e45`: 2225201920 atoms;
- `c3d74b6a-e077-45b4-b996-cf865c802096`: 2152001920 atoms.
- `49fe5fc1-5a02-4559-9adc-cc91024a1c72`: 2225201920 atoms (резерв от 23.11,
  обнаруженный на присланных снимках после освобождения предыдущих двух).

Повторно освобождённый резерв не вычитается ещё раз. Изменившаяся сумма,
provider usage или состояние блокируют применение существующими проверками;
будущие и посторонние запросы не включаются в подтверждение владельца.
Provider usage остаётся unknown, а факт операторского подтверждения сохраняется
отдельно. Плановые задания не вызывают этот адресный режим.

`--resume-setup` пропускает уже выполненные очистку релизов и замер живых БД;
его можно сочетать с адресным подтверждением резервов. Ввод в SSH нормализует
CR/Enter и временно включает canonical mode, включая мобильные терминалы;
секреты не эхоятся. Исходные настройки TTY восстанавливаются также при Ctrl+C.

Временные PostgreSQL контейнеры задают `PGDATA=/var/lib/postgresql` равным
собственному приватному bind mount. Это позволяет штатному entrypoint сменить
владельца каталога, не оставляя root-owned 0700 родитель над вложенным PGDATA
PostgreSQL 18. Ожидание ограничено 120 секундами, сообщает прогресс и проверяет
финальный postgres PID 1, а не временный сервер инициализации. CI воспроизводит
прежний отказ в доступе и проверяет реальное восстановление синтетического dump
и модель 5000 операций на PostgreSQL 18 без сети и опубликованных портов.

Синтетический замер имеет `applicationSchemaBenchmark=false`: он измеряет
описанную воспроизводимую модель PostgreSQL с индексами/JSON/историей, а не
выдаёт модель за полный production benchmark всех таблиц CashNeuro.
