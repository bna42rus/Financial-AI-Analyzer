## Editors and calculation authority

The authenticated operation drawer now creates and edits explicit components. Signed decimal amounts are parsed to bounded integer minor units; their algebraic sum must equal the effective operation amount. Each part has its own type, meaning, category and subcategory. Existing IDs are retained. Components replace the parent in calculations, including a split into categories with the same financial role. A removed part is retired, preserving references and dependency warnings. Returning to a whole operation is an explicit empty `components` intent: all active parts are retired and decomposition becomes false. The server previews any affected links and totals before confirmation; it never silently retargets a link.

Existing component facets omitted from an edit retain their stored source, confidence and verification. Merely changing an amount or type does not turn an automatic loan principal into a verified decision. Explicitly chosen meanings/categories use the existing independent user verification. New automatic parts remain unresolved unless the existing loan model supplies their meaning. Changing a parent category explicitly clears the subcategory. Component assignments do not rewrite the parent’s banking or semantic facts.

The same drawer creates and edits refunds, own transfers, compensation, reversal, credit-card repayment and debt-repayment links. Users select direction, counterpart, endpoint on each side, positive allocation amount and confirmed/candidate/rejected status. The counterpart picker uses a fresh complete authenticated workspace snapshot, independently of the list’s period/category filters, and searches locally. An epoch mismatch requires reopening the editor on a fresh operation snapshot.

Endpoint choices use server-projected parts. `componentId` and `allocationId` remain separate: an allocation derived from a component uses the allocation selector, without passing its component provenance as a second selector. Projection IDs are opaque and are never parsed. An existing consumed endpoint stays available for editing through its retained selector; inactive, cyclic, ambiguous, over-capacity or contradictory confirmed decisions are independently refused by the existing server graph. Candidate/rejected decisions remain saved but do not affect totals. A partial own transfer retains an unresolved remainder; an explicit fee component remains an expense. User-confirmed facets cannot be overridden by a link.

## Preview, conflict and recovery

Both editors use the existing `/finance/preview` and `/finance/commit` flow. The drawer displays the server’s before/after expenses, income, unresolved and neutral totals, affected-operation count and link-conflict count for the entire history. Cancelling a preview makes no financial change. Confirmation rechecks session access, entitlement, tenant ownership, generation, revision and dependencies. New edits/drawer dismissal remain blocked during an uncertain write. A lost acknowledgement retries the exact action/commit, without creating a second allocation.

A relation/component conflict cannot be replayed over a newer snapshot with the ordinary operation-field override. The user must refresh, select current parts and request new consequences. A confirmed change with a failed reload stays read-only until refreshed. Generation/reset, deletion and suspended access cannot be bypassed through this flow. History and dependency-aware Undo remain available; original bank observations stay immutable. A read-only breakdown shows final server-projected parts, categories, financial meanings and excluded states, without counting their parent again. Positive expense parts are labelled as expense reductions. No financial browser persistence, external AI or additional provider is introduced.

## Validation and operational scope

New pure checks exercise exact cents/bounds, unchanged facet omission, stable IDs, allocation/component selector separation, positive link amounts, explicit confirmation, lost commit retry and stale-set refusal. PostgreSQL/HTTP checks cover facet preservation, retirement/dependency previews, Undo, effective corrections and cross-tenant refusal. Full real HTTP/PostgreSQL desktop/mobile journeys cover a category split, refund allocation across purchase components, rejected over-allocation, successful commit with lost acknowledgement, nested reversal, partial own transfer, fee split and relinking, rejected-status Undo, concurrent preview invalidation, persistence, unchanged bank facts and suspended access. Synthetic browser scenarios also cover local validation, preview cancellation, opaque selectors and stale snapshots. Exact-head run evidence is recorded in the PR after completion.
