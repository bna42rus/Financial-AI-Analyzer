# Отказ отправки Анализатора: 2 ноября 2026

Владелец подтвердил отсутствие списания Cloud.ru по незавершённому вызову 2 ноября. В локальном учёте осталось резервирование, а не подтверждённая оплата. Старый код потерял HTTP-статус/сетевую причину, поэтому по сохранённому результату нельзя установить исходную причину отказа.

Исправления:

- Runtime ожидает единственный ответ до 90 секунд вместо 30. Это запас времени, а не доказательство, что прошлый отказ был таймаутом. Лимиты токенов, суммы, количество вызовов и запрет автоматических повторов сохранены.
- В журнале вызова сохраняются только разрешённые коды HTTP/сети, этап проверки ответа, длительность и публичные имена параметров. Тексты ошибок провайдера, ключи и финансовые данные не сохраняются.
- `scripts/recover-unbilled-assistant-staging.py` проверяет соединение через GET `/v1/models`, без генерации. Успешный GET не доказывает работоспособность POST.
- Применение скрипта требует `--apply --attest-unbilled`. Он освобождает ровно один согласованный резерв в обоих бюджетах с частным аудитом, блокировками и проверкой исходных состояний. Потраченные суммы, время отправки, неизвестные токены и исходный ответ в диалоге сохраняются. Повторное применение не освобождает деньги второй раз.
- Новый неизвестный вызов по-прежнему требует проверки; автоматического списания или обнуления неизвестных расходов нет.

Проверки: журнал после перезапуска сохраняет безопасные причины HTTP 400, DNS и таймаута без повторного POST; неизвестный расход остаётся неизвестным; приватные поля отклоняются. PostgreSQL-проверка использует реальные ограничения схемы, проверяет освобождение обоих резервов, сохранение расходов и микросекунд, повторный запуск и отказ при изменившихся суммах/токенах.

Приёмка на сервере: проверить результат GET, применить адресную сверку, установить runtime, затем отправить один новый вопрос на сайте. До ответа реального провайдера работоспособность live Анализатора не подтверждена.

## Уточнение выбранного периода

Последняя диагностика подтвердила получение обоих ответов модели (`understand`, `check_changes`). Итог `CONDITION_UNCLEAR` — запрос уточнения, а не ошибка доставки.

В коде найдена отдельная ошибка: наличие выбранного периода определялось наличием обеих дат. Валидный глобальный снимок задаёт период и без границ («вся история»), и с одной границей. Такие режимы теперь доступны через `use_current`; даты остаются на сервере. Регрессия проверяет снятие прежних дат диалога при переходе на эти режимы; неизвестные даты личных событий по-прежнему требуют уточнения.

Во время запроса интерфейс сразу показывает новый вопрос и состояние ожидания. После сохранения результата временная строка заменяется сообщением из БД. Прокрутка отслеживает идентификатор последнего сообщения, включая случаи, когда количество сообщений не изменилось. Это не повторяет запрос к модели и не меняет историю старых ошибок.
