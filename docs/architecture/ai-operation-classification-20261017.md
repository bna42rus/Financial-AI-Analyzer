# AI-категоризация операций — Staging

Продолжение объединённого релиза, без изменения банковских фактов, сумм,
дедупликации, links/components и пользовательской логики. Основание:
Master Specification §§7.4, 16.3, 17, 18.2/18.10–18.12, 29.2 и 45–46.

## Что подключено

После завершения импорта worker сохраняет только tenant/generation в очередь.
Finance API с явным `CLASSIFICATION_ENABLED=1` обрабатывает очередь отдельным
фоновым проходом; ключ остаётся в приватном Finance API credential. В Control,
mail и import worker ключ не передаётся. Для ранее загруженных операций есть
кнопка «Разобрать категории загруженных операций». Есть состояние выполнения,
обновление рабочего экрана и история AI-назначений в карточке операции.

Первый контракт назначает category/subcategory для expense/income. Он не меняет
kind, role, суммы, source facts, links, allocations или components. Неразрешённый
финансовый смысл и активные components остаются для Review, а не угадываются.

На внешнюю модель передаются только конечные банковские признаки: известное
каноническое имя магазина из текущего privacy-профиля, kind/role и очищенный
каталог категорий с временными ссылками. Нет исходных описаний, комментариев,
дат, сумм, account/transaction/user IDs, email, HMAC, получателей или файлов.
Неизвестный магазин без достаточных безопасных признаков остаётся для Review.
Это намеренно не расширяет существующий local-first privacy-контракт.

Модель выбирает только существующие видимые категории подходящего role и
правильную пару parent/child. Новые категории не создаёт. Отсутствующее такси
не подменяется общественным транспортом. Маркетплейс без состава покупки не
доказывает конкретную товарную категорию.

## Защита решений и повторов

Каждый facet имеет source/confidence. User/manual verification, personal/global
rules и подтверждённые детерминированные категории защищены. Текущие правила,
права доступа и generation/key повторно проверяются до отправки и применения.
Если во время HTTP появилась ручная правка или новая более сильная категория,
ответ AI её не переписывает. При удалении/reset результат не создаёт данные заново.

90–100: уверенное назначение; 70–89: назначение с Review; ниже 70: без категории,
с низкой уверенностью и Review. Банковские source facts остаются неизменными.
В private tenant cache ключ входят engine version, каталог с ID/иерархией и
конечные признаки. Повторяющиеся магазины объединяются в одну модельную запись.
Результат можно применить к новой загрузке этого пользователя без нового POST.
Кэш не переносится между пользователями; reset/key rotation его удаляет.

Транзакции БД короткие; HTTP выполняется после committed reservation. Session
advisory lock не даёт двум API/worker процессам отправить один проход одновременно.
Sent/unknown не повторяются автоматически даже после перезапуска. При ошибке AI
валидный импорт сохраняется, категоризация может быть заблокирована до разбора.
Произвольный raw ответ и скрытое reasoning не сохраняются: только проверенные
конечные decisions, версия engine и изменения category/subcategory.

## Стоимость и выпуск

Step `classification` использует прежний проектный бюджет, вызовы и unknown holds,
но не увеличивает `analyzer_usage` и не списывает `ai_user_budget`. Обход лимитов
чата для автоматической классификации не создаёт дополнительный проектный лимит.

Аддитивная миграция `0028_ai_classification.sql` создаёт очередь, private runs/cache
и историю назначений с RLS/FK/cascade. Обновление вызывается с
`prepare-staging-release.sh <repo> <sha> --enable-classification`.
Оно проверяет старую source binding, сохраняет dump и прежнюю приватную настройку,
меняет в ней только source SHA и выполняет два явных платных synthetic smoke:
известные магазины/маркетплейс и такси без категории такси. Вызовы входят в прежний
лимит; quota, ключ, admission, цена, даты и остатки не обнуляются/не продлеваются.
Затем переключаются Staging UI/API/import worker. При ошибке восстанавливаются
старая binding, службы и frontend. Миграция, стоимость и уже сохранённые решения
не откатываются автоматически. Production не включается.

Тариф/допуск проверяются существующим валидатором: если старый pilot истёк или
исчерпан, установка останавливается. Новый бюджет не выпускается автоматически.

Проверки: closed protocol/privacy/confidence, настоящие HTTP/PG границы с fake
провайдером, текущий import/assistant regression, desktop/mobile built UI,
отдельные synthetic POST при установке. Успех software tests сам по себе не
считается доказательством качества ответов живой модели или приёмкой продукта.
