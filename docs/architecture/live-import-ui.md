# Authenticated PDF import UI — Development

The API-connected application now opens saved finance data rather than demo fixtures. Selecting PDFs automatically runs the existing device-only parser, local HMAC preparation and finite `bank-source/1` profile, then sends only the closed prepared JSON batch to `/finance/import-accept`. No additional upload, AI or external service is introduced. The original demo remains available without `VITE_API_ORIGIN`; it does not import files.

## Lifecycle and recovery

- File selection/drop starts local preparation immediately. Unsupported/empty/oversize files appear as local technical issues; valid files continue. Password-required files remain in device memory for an explicit local attempt with fresh file IDs and a cleared password input. Neither filenames nor passwords enter the server contract.
- Closing local preparation aborts it; a late result cannot submit. Leaving the authenticated workspace disposes file references, temporary preparation and any unsent prepared batch. Raw bytes are cleared by the existing reader/helper; JavaScript strings and original `File` objects depend on garbage collection.
- A failed/uncertain handoff retains the same sanitized batch only in memory. Explicit retry preserves the original batch/file IDs and content, allowing the existing server digest/idempotency check to recover a lost acknowledgement. A confirmed history result also clears the pending attempt; a late HTTP failure cannot undo it. Expired/changed preparation requires a new file selection.
- Before server acknowledgement the page warns before leaving. After acknowledgement it can close: the durable dispatch/checkpoints worker completes independently. With an uncertain unacknowledged attempt, closing the browser can lose the local prepared batch; returning discovers server-accepted work or requires file selection again.
- One active batch remains enforced by the server. The UI discovers active work first, disables new selection during it, and polls persisted state/history. It restores a result after reload without storing raw files, prepared payloads, passwords or keys in localStorage, sessionStorage or IndexedDB.

## Saved data and reporting

`GET /finance/imports` returns at most 50 tenant-owned batch metadata records, newest first. `POST /finance/imports` accepts only an optional `before` batch UUID; a tenant-owned timestamp/UUID cursor handles tied timestamps and pagination. Foreign/nonexistent cursors are rejected. The endpoint requires the same verified session, current finance access, lifecycle locking and database role as existing finance routes. Control has no route or table authority. It returns no payload, HMAC, filename, key or money. Existing `/finance/import-status` supplies the report.

The result separates distinct canonical operations (`transactionCounts`: created/existing/updated/review) from source rows and technical issues (`counts`: found/pending/notImported/removed). It lists discovered accounts, bank/file position and fixed issue labels with a local source check or reupload next step. Unreadable mandatory facts are not manufactured as transactions or semantic review items. Local file-read/format errors remain visible in the current dialog but are not persisted as raw filenames in server history.

Operations, accounts, effective fields and review reasons come from authenticated finance APIs. The overview uses the server's canonical aggregate over the entire loaded history, including component/link/refund rules; the browser does not recompute finances from demo formulas. Operation details distinguish current effective money/date from source facts. These screens currently support reading, an attention filter, history and import; full editing/review and other financial settings are separate pending work.

## Reproducible evidence and limits

Unit scenarios cover safe-only handoff, lost acknowledgement/concurrent retry, recovery and late response races, abort/disposal, local password retries, partial file failures, invalid selections and expired contexts. PostgreSQL/HTTP checks cover tenant isolation, active/suspended access, bounded history pagination with tied timestamps and reset cleanup. Desktop/mobile HTTP/browser journeys use generated artificial PDFs through the real bundled PDF worker, exercise lost acknowledgement, same-body retry, reload before worker processing, durable partial reporting, operation details, reimport without duplicate transactions, privacy boundaries, storage and suspended access. Existing parser/worker/core/security/interface scenarios remain in the full CI suite. Exact-head CI evidence belongs in the PR.

The supported observed T-Bank/Ozon/Sber templates and existing limits remain as documented in [local-bank-parsers.md](local-bank-parsers.md). A closed finite merchant/event registry does not restore arbitrary source descriptions. CSV/XLSX, local OCR, unknown-format AI structuring, strict cross-file fingerprints, remembered duplicate decisions, accepted-batch cancellation, final classification/link matching, full review/editing and real-device/Production acceptance remain pending. Baseline 1.3 and original PDF/Word are unchanged; no requirement is marked fully verified by this block.
