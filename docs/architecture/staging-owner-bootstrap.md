# Первый владелец Staging

Основание: master specification §40.1–40.17 (подтверждённая почта, выбранный владельцем пароль, обязательный TOTP администратора) и утверждённое уточнение E04 (одноразовые резервные коды). Подтверждение заявки Finance не создаёт аккаунт Control и не даёт административных полномочий.

Это локальная команда первоначальной настройки, доступная только root с интерактивным терминалом. HTTP-маршрута нет. Development seed не используется. Production запрещён. Команда подключается только к `finance_staging` на localhost:5411 от `staging_bootstrap_owner` и разблокирует настоящий KMS realm `staging/control`; переменная с открытым wrapping key не поддерживается.

Перед запуском следует установить проверенный релиз API и почтового worker с новым шаблоном `owner_email_verification`. Настройки сохраняются вне репозитория в обычном root-owned файле с правами 0600, например `/etc/cashneuro/staging/owner-bootstrap.json`. Файл содержит ровно следующие поля; значения ниже — синтетический пример, не готовые рабочие настройки:

```json
{
  "environment": "staging",
  "databaseUrl": "postgresql://staging_bootstrap_owner:REPLACE_LOCALLY@127.0.0.1:5411/finance_staging",
  "ownerEmail": "owner@example.test",
  "allowedEmails": ["owner@example.test"],
  "authorizedKeyPath": "/etc/cashneuro/kms/staging/control/authorized-key.json",
  "wrappingKeyPath": "/etc/cashneuro/kms/staging/control/wrapping-key.json"
}
```

Рабочий адрес должен совпадать с разрешённым тестовым получателем почтового worker. Секрет БД берётся локально из настроек Staging, а не вводится в командную строку и не выводится в журнал.

Из каталога `apps/api` выполните в интерактивном терминале:

```sh
sudo /usr/bin/node --import tsx src/owner-main.ts begin /etc/cashneuro/staging/owner-bootstrap.json
sudo /usr/bin/node --import tsx src/owner-main.ts complete /etc/cashneuro/staging/owner-bootstrap.json
```

Первая команда ставит письмо с кодом в зашифрованную очередь Control. Код действует 15 минут, привязан к адресу и назначению создания первого владельца. В существующей `control.auth_verification` зарезервирована запись `cashneuro-staging-first-owner-v1`, identifier `cashneuro/staging-first-owner/v1`; хранится хеш кода, а не код. Миграция не нужна. Пять неверных попыток блокируют текущий код. Повторная выдача возможна после истечения срока или блокировки; предыдущая ожидающая отправка помечается STALE.

Вторая команда скрыто запрашивает почтовый код и выбранный владельцем пароль дважды. После атомарной проверки создаёт единственный аккаунт с подтверждённой почтой и Argon2id-хешем пароля, уничтожает доказательство и оставляет `bootstrap_pending=true`. Advisory lock исключает параллельное создание второго владельца. Любой уже существующий аккаунт Control закрывает обе команды; runtime-роли не могут их выполнять.

Войдите в `https://admin.test.cashneuro.ru` через существующую парольную защиту и затем с новым паролем аккаунта. До проверки TOTP доступ имеет только scope enrollment: чтение и изменение административных данных запрещено. После настройки и проверки TOTP действует обычная авторизация Control. Восемь резервных кодов выдаются один раз; сохраните их приватно. Код из письма, пароль, ключ TOTP и резервные коды нельзя пересылать в чат или сохранять в репозитории.

До создания аккаунта можно удалить только зарезервированное ожидающее доказательство и остановить его отправку; откат кода не создаёт владельца. После создания аккаунта повторная первоначальная настройка запрещена: используйте штатные вход и восстановление доступа. Этот механизм не меняет тарифы, оплаты, доступ клиентов и данные Finance.

Проверки: конфигурация и отказ при piped input; настоящий PostgreSQL 18 с изолированной БД и ограниченными ролями; зашифрованная почтовая очередь; истечение, пять попыток, адрес, повторное использование и параллельные запросы; штатный вход с запретом админ-данных до TOTP и доступом после него. Интеграционные тесты запускаются только на отдельном одноразовом кластере через `SECURITY_TEST_DATABASE_URL`, не на установленной Staging БД.
