### Как понимать подтверждение

- **SRC (39)** — первичная страница прочитана напрямую; иногда доступен только заголовок/redirect, что специально отражено. Подтверждается оговорённый торговый профиль, не актуальный конкретный договор/получатель, юридический статус посредника за пределами прочитанного и не банковский descriptor.
- **IDX (26)** — собственная страница/первичный документ прочитаны через индексированный текст, либо прямое чтение существенно ограничено. Индекс может быть старше даты просмотра. Не выдавать за проверку текущих адресов/оплаты/оператора всех точек. URL и конкретный объём подтверждения показаны для каждой записи.
- **HIST (1)** — MP008: подтверждён прежний профиль и публичная трансформация, современную работу универсальной витрины не обещаем. Исторические товарные операции, возвраты и расчёты не исчезают. Период/вид услуги устанавливаются по операции, не по текущему имени.
- **PEND (5)** — MP033, MP034, MP036, MP038, MP054: достаточное первичное подтверждение новой записи не закрыто. Формы описаны как кандидаты, **автоматическая активация запрещена**. Ошибка доступа/CAPTCHA не доказывает закрытие. Вторичная публикация/карта/похожий домен не заменяют источник. Старый независимо принятый профиль другого раздела не выключается лишь из-за неудачного открытия страницы здесь.

## 2. Написания и ограничения

Все формы ниже — **предложенные строки распознавания**, не утверждение, что они встречались в выписке. Внутри профиля NFKC/casefold/ё-е не увеличивают счётчик; одна форма может требовать разных исходов в зависимости от контекста. Кириллическая фонетика не приказывает менять исходный алфавит display name. Название профиля в документе — метка для согласования, а не обязательное новое имя каждой операции.

1. Нормализовать регистр/повторные технические пробелы и ё-е внутри закрытой строки; сохранять исходное безопасное описание отдельно. Раздельные/слитные/дефисные варианты только из явного списка, не произвольное удаление всех разделителей.
2. Падежи буквальные, без неограниченного стемминга. «У Петровича», «в твоём доме», «фамилия», «светофор», «лаберинт» с ошибкой не автоматически сеть. Неверная раскладка, все опечатки/перестановки/дистанция редактирования и глобальная транслитерация не разрешены.
3. Кандидат с общим словом/именем требует надёжного торгового контекста/установленной identity. Подробный товарный чек для очевидного специализированного профиля не обязателен. MCC может дополнить/опровергнуть профиль, но не заменить получателя или конкретный товар. Код магазина/сумма/город не доказательство направления.
4. Полные границы слов и существенная часть продукта сохраняются. Простой WB/ВБ/MM/Маркет/DNS/КНС/NIX/Pro не положительный профиль без условий; не совпадать внутри номера, кода, домена чужой компании/слова и не отрезать конфликтующий хвост.
5. Латинские/кириллические похожие символы не заменяются глобально. Смешанные формы е2е4/e2e4 допустимы лишь в явно заданных полных вариантах; шахматный ход/код не магазин. Литерал URL в таблице не разрешает раскрыть ссылку, скрытую sanitization.
6. Конкретный продукт/услуга известной семьи важнее родителя: Ozon Premium/Банк/fresh/Travel; WB Клуб/банк/кошелёк; Магнит Косметик/Маркет/продуктовый магазин; Яндекс Go/Маркет/Плюс/Сплит; товар и плата продавца различаются. Совместное упоминание независимых брендов не выбирается первым match.
7. Производитель/бренд товара, площадка, торговый продавец, агент, курьер, банк/эквайер, точка выдачи и конечный получатель — разные роли. По названию iPhone внутри покупки не создавать продавца Apple; по адресу ГУМ не подменять отдельный магазин универмагом.
8. Все IDX/PEND/HIST и исторические ограничения сохраняются при точной форме/высокой уверенности модели/cache. Признание пользователем списка не устанавливает банковский alias или договор. При реальном конфликте identity не выдумывать получателя, даже если широкий экономический предмет установлен независимо.

## 3. Категории, финансовый смысл и правила

### Предлагаемое дополнение дерева — отдельно видно владельцу

В текущем `starter.ts` **нет узла «Техника и электроника»**. Предлагается добавить **один базовый расходный узел с этим именем, без новых подкатегорий**, для профильных покупок бытовой/цифровой/компьютерной/фототехники и аксессуаров. Это предложение входит в итоговое согласование четырёх пунктов, **категория сейчас не создана и не установлена**. Для существующего пользователя прежде использовать его собственный подходящий expense/both ID с учётом rename/hide/delete; не клонировать одноимённый узел, не делать чужой ID допустимым и не восстанавливать удалённое повторным входом. Миграцию/одноразовое добавление и release обсуждать/реализовывать позднее.

Звёздочка «Техника и электроника*» в карте ниже означает именно этот проект. До принятия и наличия подходящего собственного узла нельзя молча подставить «Товары для дома», «Маркетплейсы» или создавать новую категорию. Остальные пути ниже уже есть в starter либо явно ссылаются на ранее согласованный профиль. Пользователь может предпочесть своё дерево; имя сервиса не переименовывает его категории.

### Что изменяется в предложенной трактовке по сравнению с ранними документами

- **Ранний аудит 24.10** описывал fallback «Маркетплейсы → Прочие расходы» при отсутствии узла. Новый проект предлагает **не применять такую молчаливую подстановку**: использовать подходящий собственный узел/родитель, иначе оставить без категории с понятным предложением выбора. Это явное проектное уточнение, не утверждение, что runtime уже исправлен. Его принятие входит в общее итоговое согласование.
- **CDEK.Shopping** не объявляем юридически маркетплейсом. Предлагаем для установленного товарного выкупа без известных вещей использовать существующую аналитическую группу **«Маркетплейсы» как покупку через многокатегорийную онлайн-площадку/агента**. Такая группировка — новое явно показанное предложение для согласования, а не скрытое равенство получателей/ролей. Самостоятельная доставка/агентское вознаграждение и обычный СДЭК — отдельно по назначению.
- **Lamoda и Авито:** для установленного товарного онлайн-заказа без известного предмета допустима группа «Маркетплейсы». Доказанный конкретный предмет/личное правило выше. При подтверждённом fashion-направлении без вещи сохраняется прежняя FASH-развилка широкого родителя с Review. Само слово Авито не доказывает товарный заказ: услуга, аренда, реклама, пополнение/продажа и выплата не превращаются в покупку товаров.
- **Многопрофильные магазины не все маркетплейсы.** Розничный сайт/широкий каталог, Сима-ленд/Fix Price/универмаг/ГУМ не становятся этой категорией автоматически. Общая категория достаточна, когда установлено именно допустимое широкое направление, а не когда просто неудобно оставить вопрос открытым. Никаких новых «Разные покупки»/«Цветы»/«Бытовая техника» как дочерних узлов здесь не создаём.

### MP-U01–MP-U32

1. **MP-U01 — Раздельные identity и category.** Сначала достаточно ли оснований для торговой площадки/магазина, затем — для предмета. Узнать Ozon не значит узнать одежду. Можно знать предмет независимо от точного продавца; не придумывать merchant ради категории.
2. **MP-U02 — Очевидная покупка без лишнего Review.** Установленная обычная покупка на универсальном маркетплейсе → Маркетплейсы; установленный книжный/строительный/спортивный профиль — своя базовая категория. Детальный чек не обязателен, автокатегория не user_verified.
3. **MP-U03 — Подходящий товарный заказ маркетплейса.** MP001–005/007/014 и исторический MP008 только с допустимым периодом: без предмета → Маркетплейсы, без обязательного Review за неизвестную корзину. Конкретный товар, части и личное правило сильнее. Не назначать всем событиям бренда одну роль/категорию.
4. **MP-U04 — Авито и частные лица.** Только установленный товарный заказ через платформу допускает Маркетплейсы. Само Авито/перевод физлицу не доказывают ни товар, ни фриланс, ни платёж Авито. Известные работа/аренда/услуга/реклама/покупка автомобиля определяются по предмету и роли; ссылка на FR10/FASH090 единая.
5. **MP-U05 — CDEK.Shopping — агент.** Предложенная аналитическая группа для товарного выкупа не меняет агентскую модель. Цена товара, отдельно известная доставка/комиссия, возврат и зарубежный продавец различаются; просто СДЭК не Shopping.
6. **MP-U06 — Flowwow и Livemaster.** Многокатегорийная товарная покупка → Маркетплейсы без Review лишь за отсутствие чека. Не объявлять все заказы цветами/подарками/хобби/благотворительностью. Известный предмет/дарственная цель сильнее общего профиля.

### MP-P01–MP-P12: как параметризовать общий прогон

1. **MP-P01 — полный состав:** все 71 MP с их источником/статусом/датой и точными межраздельными связями. 39 SRC / 26 IDX / 1 HIST / 5 PEND — отдельные поля, не измеренная вероятность. Все PEND должны оставаться заблокированными; HIST требует установленного периода/смысла.
2. **MP-P02 — все формы:** 662 кандидата с явным oracle positive/conditional/negative/blocked. NFKC/casefold/ё-е и повторные пробелы по согласованным границам; case-дубли не новые aliases. Не выводить все отрицательные из одного положительного теста или все 662 формы автоматически считать положительными.
3. **MP-P03 — контекст:** начало/середина/конец безопасного текста, допустимая пунктуация, разные разделители только по списку, общий омоним/ФИО/код/название вещи/чужой суффикс/конфликт брендов, достаточные и недостаточные признаки магазина. Категория по фактам не превращает слабую identity в сильную.
4. **MP-P04 — услуги/предметы:** товар, подписка, банк/кредит/BNPL, доставка/отказ/агент, seller-услуга, подарочная цель, игровое/цифровое/учебное, личная/рабочая цель. Не полный бессмысленный Cartesian product, а все применимые границы каждого профиля.
5. **MP-P05 — финансовые facets:** kind/role/category/subcategory/link/dedupe/source/confidence/verification раздельны; purchase/refund/reversal/fee/hold/balance/transfer/payout, expense/income/neutral/unresolved/mixed только по достаточным фактам. Не превращать model confidence в измеренную вероятность.
6. **MP-P06 — дерево пользователя:** собственные expense/income/both, подходящий parent, rename/hide/delete/отсутствие категории, protected manual, пользовательский узел техники и проектный новый узел ещё не принят; иностранные ID отклоняются. Общая категория не автоматический Review за недетальность.
7. **MP-P07 — части:** обычная покупка любого продавца; 1/2/несколько/50/51 частей, остаток/превышение/валюта/копейки/границы integer; parent vs parts; сложные долг/neutral не простая purchase allocation. Общий source неизменен, distribution только effective analytics.
8. **MP-P08 — жизненный цикл:** первый импорт/повтор/обновление/отмена, ручное распределение, следующая независимая покупка, частичный возврат, конфликт зависимости, удаление/Undo, повторный commit. Фактический parent/binding/ошибка предыдущего хода не заменяется эталонным состоянием.
9. **MP-P09 — время/валюта:** исходная и банковская суммы/валюты/posted/operation даты, месячная/годовая оплата; пользовательские зоны восточнее/западнее UTC и границы суток/месяца. Выбранная продуктовая временная база и gross/net/returns одинаковы на всех экранах; не всем московское время и не произвольная амортизация платежа.
10. **MP-P10 — входные пути и безопасность:** импорт, доступные ручные preview/commit/Undo, closed Registry, model/cache, изменение доступа/удаление между preview/commit, RLS/entitlement. Для недоступного пути BLOCKED с причиной, не PASS по похожему экрану. Реальные выписки/секреты/частные данные для этих тестов не использовать.
11. **MP-P11 — аналитика:** операции/поиск/фильтры продавца/категорий, обзор/графики/бюджеты/Analyzer; одна согласованная выборка, суммы и детализация, явный текстовый override контекста Analyzer. Не считать родителя с частями и не переносить расход в другой период молча.
12. **MP-P12 — воспроизводимость и расходы:** версии каталога/данных/схемы/Registry/policy/cache, очищенный synthetic input, original raw ответа/usage/валидатор/app outcome, expected/actual/Review reason/фактический parent. Архивный replay и новый POST отдельно, неизменяемый архив ошибки сохраняется; старый расход/общий согласованный лимит не обнулять, неизвестный отправленный запрос автоматически не повторять. Этот документ не продлевает истёкший runtime admission и не запускает платный прогон.

### Как принимать результаты позже

Для каждого случая хранить PASS / FAIL / BLOCKED / NOT_RUN, отдельно причину: источник/модель/схема/evidence/compiler/финансовый учёт/UI/access/неверный oracle. По применимости — marketplace/product/merchant/agent identity, собственные category IDs/пути, role/kind, source/confidence/verification, review flag и понятная причина, суммы/валюты/parts/links/totals/source identity и actual parent. Не требовать выдуманного ID/поля неприменимого facet.

Защитный отказ приложения на чужую категорию может быть PASS защиты и FAIL ответа модели одновременно. Не менять исходный неверный ответ на исправленную категорию и не выдавать обход ошибки за точность модели. Доступный широкий профиль без чека — полноценный правильный результат, а пустая категория не универсальная стратегия безопасности.

Результат документа сейчас: полный проект согласован владельцем. Проверяются лишь уникальность/непрерывность 71 MP / 32 U / 36 C / 72 T / 12 P, 662 формы и счётчик статусов, корректность ссылок/Markdown и отсутствие runtime-изменений. **Ни один MP-T здесь не выполнен.** Будущий общий прогон должен покрыть все применимые ветви и текущие ограничения; несколько модельных ответов не доказывают точность всего каталога.
