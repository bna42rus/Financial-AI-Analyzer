## 3. Категории, приоритеты, Review и разрешение конфликтов

### Детерминированная последовательность будущей обработки

1. Проверить реальное финансовое событие/роль в существующей модели; сохранить manual/verified/parts/личные правила.
2. Из разрешённого предметного контекста собрать все целые конечные кандидаты ACT; хранить основание/версию, не исполнять банковский текст как инструкции.
3. Отсечь отрицание/цитату/обычное слово/товары для услуги; учесть специфический предмет и agreed merchant default. Реальное противоречие не решать длиной строки или порядком словаря.
4. Выбрать собственный актуальный совместимый ID по binding/доказанной семантике. Наличие похожего имени — кандидат, не автоматическое разрешение; чужие/скрытые/удалённые узлы не использовать для нового global assignment.
5. Очевидное — обычная категория без лишнего Review. Обоснованное сомнение — видимое provisional и конкретная причина. Без основания/нужного узла — деятельность сохранена, выбор/достоверный родитель, импорт не блокируется.
6. Пересчёт/экран/Analyzer используют существующие effective fields, роль и parts; preview/commit проверяются сервером заново. Ни одного нового права/изменения финансового source из ACT.

### Общие правила ACT-U01–U32

| ID | Правило | Полный ожидаемый контракт |
|---|---|---|
| ACT-U01 | Разделение смыслов | Результат сначала activity/subject/evidence, затем категория в собственном дереве. Деятельность не merchant identity, не kind/role и не authority на действие. |
| ACT-U02 | Источник и проекция | Банковский текст/дата/сумма/source IDs/HMAC/dedupe неизменны. Нормализация существует только в отдельной поисковой проекции с сохранённым происхождением. |
