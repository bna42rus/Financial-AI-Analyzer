## 2. Полные конечные написания и отрицательные контексты

Это весь конечный inventory версии /2. Включены прежние формы, новые русские падежи/множественное число/составные слова, явно выбранная латиница/смешанные символы и материализованные варианты ACT-TR1. Это кандидаты с обязательным предметным контекстом, не новые банковские наблюдения. Общая транслитерация/морфология/fuzzy во время исполнения не разрешены. Краткие и межъязыковые формы подчиняются ACT-G01–G09; правила композиции ACT-M01–M08 не требуют буквального слова продукты.

## 3. Категории, приоритеты, Review и разрешение конфликтов

### Детерминированная последовательность будущей обработки

1. Проверить реальное финансовое событие/роль в существующей модели; сохранить manual/verified/parts/личные правила.
2. Из разрешённого предметного контекста собрать все целые конечные кандидаты ACT; хранить основание/версию, не исполнять банковский текст как инструкции.
3. Отсечь отрицание/цитату/обычное слово/товары для услуги; учесть специфический предмет и agreed merchant default. Реальное противоречие не решать длиной строки или порядком словаря.
4. Выбрать собственный актуальный совместимый ID по binding/доказанной семантике. Наличие похожего имени — кандидат, не автоматическое разрешение; чужие/скрытые/удалённые узлы не использовать для нового global assignment.
5. Очевидное — обычная категория без лишнего Review. Обоснованное сомнение — видимое provisional и конкретная причина. Без основания/нужного узла — деятельность сохранена, выбор/достоверный родитель, импорт не блокируется.
6. Пересчёт/экран/Analyzer используют существующие effective fields, роль и parts; preview/commit проверяются сервером заново. Ни одного нового права/изменения финансового source из ACT.

### Деятельность плюс способ получения — ACT-M01–M08

Имя магазина берётся из прежнего merchant inventory со всеми его допущенными падежами/латиницей, а не из нового параллельного списка. Известный профиль и модификатор рассматриваются совместно в пределах одного реального оплаченного заказа. «Доставка из Пятёрочки» не обязана содержать слово продукты. Доставка бесплатно — тоже способ получения, не вторая трата.

### Обязательная параметризация будущих проверок

- Все конечные формы каждой записи; NFKC/регистр/ё-е/Unicode combining marks, соседние цифры, дефисы, слэш, границы, смешанные символы из inventory и похожие вне него. Не одна проверка на все морфологические формы.
- Merchant/service field против адреса/реквизита/цитаты/названия книги/комментария/negation; модель и локальная ветка должны уважать один предмет/контекст.
- Собственные rename/nesting/role/both; несколько подходящих ID; hidden/deleted/чужие ID; conscious parent-only; новое/старое дерево, отсутствие целевых rollout-узлов.
- Обычная покупка/refund/hold/входящее/собственный transfer/комиссия/кредит/баланс; Cashflow/Economic; source-local дата/profile today; RUB/integer parts.
- Подтверждённый выбор/личные specific/general rules/cache/version/reimport/deletion/generation; никакой смены source/dedupe/HMAC или переноса split новой покупке.
- Import/Operations/Review/card/search/filter/Обзор/Бюджеты/Analyzer/export показывают одинаковые effective категории/parts/роли; provisional с причиной, не user_verified; независимый Review роли/links не стирается.
- Privacy sanitizer, банковский текст как недоверенный ввод, server ownership/access/Registry до preview и перед commit, stale revision/deleted scope.
- Модельный прогон отдельно при действующем лимите; локальный словарь/AI/cache сравнивать по смыслу и всем условиям. В этом шаге новых paid POST нет.
